## Systemic findings

These were reached independently by several reviewers on different surfaces. They are defects in
shared code, not per-page nits, and each is one fix that closes many findings.

### S1 — The mobile layout is broken app-wide (Critical ×4)

`globals.css:974-980` defines `.sidebar-inset { padding-left: 14rem }` with **no media query**, and
`app-shell.tsx:25-28` applies it to `<main>` unconditionally, while the sidebar itself is
`hidden lg:flex` and `useSidebar` defaults `isOpen: true`. On a 390px phone the content box is
390 − 224 = 166px, less 24px of `.page-container` gutters ≈ **118px of usable width** behind an empty
224px gutter with no sidebar to explain it.

Compounding it, `BottomTabBar` is `fixed bottom-0 h-16` below `lg` while `<main>` has no matching
bottom padding — so the last ~40px of every page sits under the bar permanently. On the list surfaces
the occluded strip is exactly the result count and pagination, which makes page 2+ unreachable on
phone.

Raised by: persons list, relations, events list, sources list, source detail, person detail.
The overlay declares tablet and phone as explicit targets (iPad at archives, smartphone for the
student persona). **Not browser-measured** — see _Measured vs. inferred_ below.

### S2 — The platform's touch-target rule is implemented nowhere (Critical ×3, Warning ×8)

A repo-wide grep for `pointer: coarse` / `min-h-11` / `44px` returns exactly one hit: an unrelated
line-height comment at `globals.css:61`. The overlay's Touch-First section requires 44×44 on
`pointer: coarse` or viewport < 1024px "applied via a dedicated media-query block rather than
shrinking desktop hit areas". No such block exists.

Several targets also miss WCAG 2.5.8's 24×24 AA floor independently of the platform rule:
the password show/hide button (16×16, `LoginForm`, `RegisterForm`, `ResetPasswordForm`), the
sources-table edit icon (~16×16), the evidence-count badge (~20×19), the sort-header buttons (~16px),
and the dialog close control (16×16). Selection checkboxes are 16×16 and are the entry point to the
destructive bulk-delete path.

### S3 — A failed fetch renders as authoritative "nothing here" (Critical ×4)

The pattern `if (res.ok) { … }` with no `else` and no `catch` recurs across
`RelationsDataTable`, `EventTypeSettingsTable`, `RelationTypesTable`, `PropertyEvidenceBadge`,
`EntityEvidenceTab` and `ActivityLog`. A 500, a 403 or a dropped connection produces the same
rendered result as a successful empty response — the empty state.

On an authority-maintenance table this reads as "no event types exist" and invites the archivist to
create duplicates. On the evidence surfaces it is worse: in a claim-integrity application, "the
evidence request failed" rendering as "this claim has no evidence" is a correctness-of-record defect,
not a missing loading state.

### S4 — Soft delete has no recovery path anywhere (Critical ×3)

`Person`, `Event`, `Source` and `Relation` all carry `deleted_at`, and the delete copy tells users the
record is only _marked_ deleted. Every occurrence of `deleted_at` in `src/` is a `deleted_at: null`
filter — grep-verified by three reviewers. There is no trash view, no restore route, no undo on any
success toast. The German confirm copy instructs the user to "Kontaktieren Sie den Administrator zur
Wiederherstellung", which confirms the overlay's "surfaced and recoverable through clear UI" rule is
unimplemented rather than deliberately declined.

A deleted record's own URL then 404s with no indication it ever existed.

### S5 — Attribution is fetched and thrown away (Critical ×2, Warning ×5)

The overlay's Mental Model Rule requires "who created/changed it and when" to surface automatically
and persistently on every record. `created_by_id`, `created_at` and `updated_at` are queried and
passed into the components on nearly every detail and edit surface, then never rendered. Where
attribution _does_ render, it is `created_by_id.slice(0, 8)` — eight characters of an opaque CUID,
with the full CUID in a hover title. It identifies nobody, and `updated_at` is rendered nowhere at all.

For this audience the overlay classes human attribution as a standing trust signal, not merely an
audit feature. `EventType` and `RelationType` have no `created_by_id` column at all, so those two
surfaces cannot be fixed in the UI alone.

### S6 — Certainty and evidence are invisible at list level (Critical ×2, Warning ×4)

The Mental Model Rule requires certainty and evidence count visible **at every level** without hover
or click. Every list surface fetches the certainty fields into its row type and then discards them —
`formatPartialDate()` takes no certainty argument, so a Possible birth year and a Certain one render
identically across 25 rows. The sub-events table on the event detail page does the same.

Two inversions make it worse where certainty _is_ shown:

- `EventDetailCard.tsx:51` suppresses the badge when certainty is `UNKNOWN`, so a date a researcher
  explicitly assessed as uncertain renders identically to one nobody has assessed — the precise
  opposite of what a four-value scale is for.
- The unevidenced warning fires on `hasCertainty={hasStartDate}` — i.e. whenever a date exists —
  so an honest `UNKNOWN` non-claim is flagged as a problem, diluting the signal that should mark a
  _high-certainty_ claim with zero evidence.

The `.certainty-unevidenced` utility and the `Badge variant="unevidenced"` both exist in the design
system and are referenced by nothing. Where the unevidenced state does render, its entire content is
the digit `0` — the word "Unevidenced"/"Unbelegt" appears in no message file.

### S7 — Bulk delete confirms the wrong entity (Critical)

`BulkDeleteDialog.tsx:34` is `useTranslations("persons.bulk")` with no namespace prop, and the
`title`/`description` props exist but are passed by no caller. Deleting on the **Events** and
**Sources** lists therefore asks _"{count} Personen löschen?"_ — a wrong-entity confirmation on an
irreversible action. The correct `events.bulk.*` keys already exist, unused.

Direction confirmed by the persons-list reviewer: the namespace is correct on persons, which is
exactly why the other two surfaces are wrong.

Adjacent, same component: selection state survives pagination while the header checkbox is computed
from the current page only — so one click can clear, or delete, rows the user cannot see.

### S8 — i18n leaks in both directions (Critical ×2, Warning ×9)

The app is German-default with an English locale, and both directions are broken:

- **English shown to German users:** `"Cancel"` hardcoded in `BulkDeleteDialog`, `PersonForm`,
  `DeleteEventButton`, `DeletePersonButton`; `aria-label="Edit"`, `aria-label="Show password"`,
  `aria-label="Language switcher"`.
- **German shown to English users:** `ActivityLog`'s entire relative-time formatter
  (`"gerade eben"`, `"vor 3 Tagen"`, `toLocaleDateString("de")`), `"Mehr laden"`,
  `"Keine Nachweise vorhanden."`, `"Person gespeichert."`, and hardcoded `"Person"/"Personen"` and
  `"Quelle"/"Quellen"` pluralisation in result counts.
- **Raw keys and zod defaults rendered to users:** several schemas are declared at module scope where
  `t()` is unavailable, so `z.string().min(1)` renders the English internal default
  `"String must contain at least 1 character(s)"`, and `superRefine` rules render their raw keys
  verbatim — `month_requires_year`, `auth.errors.passwordMismatch`. Correct translations exist in
  both locale files and are simply never wired. Confirmed by executing the schemas against the
  installed zod 3.25.76, not by reading them.

Count-bearing strings use no ICU plural syntax, so the single-item case reads "1 Personen löschen?"
and "Delete 1 persons?".

### S9 — No unsaved-work protection anywhere (Critical ×2, Warning ×4)

Grep for `isDirty` / `beforeunload` / `unsaved` across `src/` returns **zero hits**. Every form —
including the edit forms, where the discarded work is modification of an existing curated record —
loses everything to Cancel, browser Back, a sidebar click or a refresh, with no warning, no draft and
no undo. `EventForm` has no `onCancel` prop at all and calls `router.back()`, which on a deep link or
after a refresh leaves the application entirely.

### S10 — The verification flow has no exit (Critical)

There is **no resend-verification capability anywhere in the product** — `src/app/api/auth/` contains
only `[...nextauth]`, `forgot-password`, `register`, `reset-password`, `verify-email`. The verify
page's only recovery action, labelled "Neuen Link anfordern", points at `/auth/forgot-password`,
which sends a **password-reset** email. A user whose verification link expired cannot obtain a new
one by any path, and the login form's "confirm your email first" message offers no resend either.

Compounding: the API collapses "already used" and "expired" into one `TOKEN_EXPIRED` code, so
refreshing after a successful verification tells the user their link expired and pushes them toward
that dead end. And `register`'s route deliberately swallows a failed `sendVerificationEmail` and still
returns 201 with "Verifizierungs-E-Mail gesendet" — asserting the mail was sent in exactly the case
where it was not.

### S11 — Shared auth chrome (Critical ×2, Warning ×3)

Corroborated by all five auth reviewers; one fix each, not five:

- `(auth)/layout.tsx` renders no `<main>` landmark — the only `<main>` in the app is in `app-shell.tsx`,
  which the auth group does not use. No skip target on the entire unauthenticated flow.
- `CardTitle` renders a `<div>`, so every auth page's own title is outside the heading tree and the
  sole `<h1>` is the "Evidoxa" wordmark. A heading-list navigation cannot distinguish one auth page
  from another.
- `min-h-screen` (100vh) rather than `min-h-dvh` on a declared mobile target.
- `<html lang="de">` is hardcoded in `src/app/layout.tsx` while the route tree serves `/en/*` in
  English — an English screen reader speaks English content with German phonemes (WCAG 3.1.1).

### S12 — Loading states are spinners where the platform mandates skeletons (Critical ×2, Warning ×4)

The overlay's Performance-UX rule is explicit, and `Skeleton` / `PageSkeleton` /
`.animate-skeleton-pulse` all exist with a correct reduced-motion variant at `globals.css:845`. The
tab content areas and settings tables nonetheless use a bare `<Loader2 className="animate-spin">`
with no text, no `role="status"` and no accessible name — so a screen-reader user gets silence during
load. Under `prefers-reduced-motion` the global reset at `globals.css:559-567` forces
`animation-iteration-count: 1`, freezing the spinner into a static glyph: the animation is
load-bearing for the entire meaning of the state.

The route-level `loading.tsx` files are conformant and use the correct skeleton pattern; the defect is
confined to in-component loading states.

requests to settle.

Two of the highest-impact items in this report are in the inferred column. Confirm S1 in a browser at
375px before scheduling work against it.

## Not fixed here, and why

This audit is report-only. Three classes of finding additionally need a decision that is not a UI fix:

**Schema decisions.** The DACH name rule cannot be satisfied by the interface: `Person` has only
`first_name`/`last_name` — no academic-title field and no particle-aware sort key — so
"Prof. Dr." must be typed into a name field, and "von Dalberg" sorts under V. Likewise attribution on
`EventType`/`RelationType`, and the archivist's structured archive/fond/series/item reference against
today's two free-text fields.

**Product decisions.** `min(1)` on the year field makes BCE and year-0 events unrecordable in a
historical-research product. The password strength meter scores rule-compliance and then labels the
result "Sehr stark", so `Passwort1!` reads as very strong — a confidence claim the system has not
earned, which for this explicitly skeptical audience is a trust cost.

**Backlog.** Per `CLAUDE.md`, findings that outlive the current task belong in GitHub Issues, not in
a chat log or this file alone. The systemic findings S1–S12 are each a good issue candidate — they are
shared-code defects with a single fix and many dependent findings. One reviewer checked the 13 open
issues and found none of this tracked; the closest, #14 "Loading & performance", is partially
explained by S12. **No issues were filed by this audit** — filing is your call.

## Flows

Four surfaces are typed `flow-member`: `auth/register`, `auth/verify`, `auth/forgot-password`,
`auth/reset-password`. Each was reviewed individually; cross-surface IA was deliberately not analysed
here. S10 in particular is a flow-level defect visible from three separate surfaces, and the
enumeration asymmetry between register (which states definitively that an address is already
registered) and forgot-password (which deliberately refuses to say) is a cross-surface disclosure
question. Route these through `/ux` flows for the information-architect.
