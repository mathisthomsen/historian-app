# Evidoxa — Full Project Review

**Date:** 2026-07-13
**Branch reviewed:** `main` (commit `3581d0d`)
**Scope:** consistency & coding standards, security, API design, database model & design, frontend / design-system / a11y / performance, and spec/roadmap compliance for Epics 1.1 – 2.4 plus cleanup specs.
**Method:** six parallel specialist reviews, each reading the real source (no assumptions). Findings below were verified in code with `file:line` evidence; items flagged by more than one reviewer are marked **[corroborated ×N]** and carry the highest confidence.

> This document is analysis and recommendation only. Nothing has been implemented or changed. Fix recommendations are concrete but not applied.

## 1. Executive Summary

The codebase is, on the whole, **disciplined and honestly built**. TypeScript hygiene is excellent (zero `any`, strict compiler with `noUncheckedIndexedAccess`/`exactOptionalPropertyTypes`, perfect 427/427 i18n key parity), the auth token flows are cryptographically sound, Prisma soft-delete is thoughtfully designed, and every epic's progress docs match reality — all 9 recorded `2-4-delta` gaps are genuinely fixed and test counts (239 unit / verified E2E) are accurate.

The problems cluster into **five themes**:

1. **A tenant-isolation hole (Critical).** Three list endpoints trust an attacker-supplied `projectId` with no membership check — independently found by the security, API, and database reviews.
2. **A production credential leak (Critical).** CI seeds the live database with a well-known admin login on every deploy, and the API is reachable behind the holding page.
3. **Epic-boundary drift.** Each epic (2.1 → 2.4) invented slightly different conventions — error shapes, pagination envelopes, bulk contracts, Zod schema placement, file naming — and earlier epics were never backfilled. This drift has already produced real user-facing bugs.
4. **i18n regression in the relations feature.** Epic 2.4 was built German-first; hardcoded German strings and raw Zod error keys break the English locale and screen-reader labeling.
5. **Weakened quality gates & undocumented lockdown.** CI deploys to production even when E2E fails, the whole app is hidden behind an undocumented holding page, and the 80% coverage target is configured but never enforced.

1. **Add the project-membership check** to `GET /api/persons`, `/api/events`, `/api/sources` (Critical IDOR). ~6 lines each; a shared helper fixes it once.

## 2. Critical Findings

### C1 — Cross-tenant read: list endpoints trust attacker-supplied `projectId` **[corroborated ×3: Security H1, API C1, DB 3.1]**

**Files:** `src/app/api/persons/route.ts:115`, `src/app/api/events/route.ts:131`, `src/app/api/sources/route.ts:74`

All three GET list handlers resolve `const projectId = parsed.data.projectId ?? user.projectId` and query directly, with **no `userProject` membership check**. Every other list endpoint (`relations/route.ts:185-193`, `property-evidence`, `relation-types`, `event-types`, `entities/.../activity`) verifies membership first — these three are the exception.

**Exploit:** Any authenticated user sends `GET /api/persons?projectId=<victim_project_cuid>` and receives the full paginated person list (names, birth/death data) of a project they are not a member of. Same for events and sources. Aggravating factors: the seed project ID is the fixed, guessable string `seed-project-demo` (`prisma/seed.ts:35`), and results are cached in **shared Redis** keyed only by project+params (`persons/route.ts:123-126`), so cross-tenant data also poisons/serves via the cache.

**Fix:** After resolving `projectId`, add the membership guard already used at `relations/route.ts:185`, ideally via a shared `requireProjectMembership(userId, projectId, roles?)` helper (see §7 H-a):

```ts
const membership = await prisma.userProject.findFirst({
  where: { user_id: user.id, project_id: projectId },
});
if (!membership) return jsonError(403, "FORBIDDEN");
```

Add the check **before** the cache lookup, not after.

### C2 — Production database seeded with a known admin credential on every deploy **[Security C1]**

**Files:** `prisma/seed.ts:99-114`, `.github/workflows/ci.yml:99-103`

The seed upserts `admin@evidoxa.dev` with `bcrypt.hash("Demo1234!", 10)` and a verified email, with **no `NODE_ENV`/production guard**. CI runs `pnpm prisma db seed` against `DATABASE_URL_UNPOOLED` (the production Neon DB) on every push to `main`. The upsert is idempotent by email, so each deploy re-establishes the account and resets its password even if it was changed or deleted.

**Exploit:** The holding-page lockdown explicitly lets `/api/*` through (`auth.config.ts:41`), so an attacker POSTs to the credentials callback with `admin@evidoxa.dev` / `Demo1234!` and gets an authenticated session. The "coming soon" page does not protect the API.

**Fix:** Guard the demo user behind `if (process.env.NODE_ENV !== "production")`, or drop the seed step from the deploy job, or generate a random password printed only to CI logs. **Immediately rotate or remove `admin@evidoxa.dev` in the live database** regardless of the code fix.
